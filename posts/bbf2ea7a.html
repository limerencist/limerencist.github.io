Jenkins 流水線腳本示例

更新於2023-06-06|ops
|字數統計:3.7k|閱讀時間:17分鐘|瀏覽量:

  在這個 IT 行業盛行 Devops 的年代，使用自動化工具來實現應用的 CI/CD 必不可少。而在實際工作中，一般使用 Jenkins 並撰冩相應的 pipeline 來完成此類工作。

  針對不同的情況，流水線的組合也不盡相同，例如前後端編譯方式不一樣、一個 git 地址裡實際包含多個項目等等。對此，我主要總結成幾個案例以供分析（流水線中一些 git 項目地址和賬戶憑據以 xxxxx 代替）。

案例一：構建 java 後端項目

總結說明

 這是本人剛接觸 jenkins 時候撰冩的 pipeline (一些配置項可以看註釋)，主要是根據前人留下來的模版，嘗試添加 docker build（實際冩得很粗糙），並且把可以在界面上配置的一些選項和釘釘通知也轉換在腳本里（這樣就完全可以不依賴界面配置，但實際也沒有必要，純粹是早期為了學習）

案例二：構建 node 前端項目

總結說明

 這個前端項目的鏡像由 4 個靜態資源組成，分別在 4 個 git 地址上 ，在拉取代碼階段用循環拼接不同的項目地址分別拉取；

 編譯階段為了避免在 jenkins 本地安裝及配置 nodejs , 使用對應鏡像在容器中編譯成靜態資源，並且映射相關依賴目錄，加快下載依賴的速度，最後打包並壓縮成 gz 包；

 構建鏡像時候使用 docker 插件，使用 withRegistry 方法 build 並 push ；未防止機器上鏡像過多，在 push 之後進行刪除（純粹也是學習，和直接使用 docker build 或者 docker push 的命令 一樣）；

 更新階段學習使用 ansible 插件，提前冩了對應的 playbook，當時服務是用 docker-compose 編排的，更新服務只要更新鏡像即可，就冩了個 py 腳本替換 yml 裡的 image 字段，再重啟服務

案例三：構建 golang 後端項目

總結說明

 這個是最近比較折騰的一個流水線，說下總體的思路：

 使用 Jenkins 的 Kubernetes 插件，在已有的 K8s 集群中添加一個雲節點（需要提前在 Jenkins 裡配置的，具體可以看插件的說明）；

 這個雲節點會和 podTemplate 裡冩的多個容器組成一個 pod 運行 （podTemplate 裡的語法也可以使用最直接的 yaml），例如此處創建了 3 個 container；

 代碼拉取： 使用 checkout 來實現淺拷貝，加快拉取速度，以 commit id 作為之後鏡像的 tag

 代碼掃描：使用 pod 中的 sonar 容器（sonor 鏡像需要提前準備）完成掃描；

 代碼編譯：使用 pod 中的 golang 容器，利用研發在項目中撰冩的 Makefile ，執行 make linux-build 生成可執行文件（因為 go build 中依賴其他項目中的公共庫，所以這裡加了一些其他的 git config，在 podTemplate 的 envVars 中也添加了一些編譯需要的環境變量 ）; 這個 golang 容器的鏡像為了能夠免密拉取公共庫的包，配置了 git 中 ssh 的秘鑰；

 構建鏡像：這個和之前一樣，使用 Jenkins 的 docker 插件完成，稍微不同的就是單獨封裝成了一個方法，需要時候直接調用；為了避免 docker build 時上下文過大，添加 .dockerignore 文件；另外，這一步使用 pod 中的 golang 容器，在 podTemplate 的 volumes 中也添加 hostpath 實現 docker in docker ；

 更新服務：使用 pod中的 kubectl 容器，根據不同分支選擇對應 K8s 集群環境（不同的 kubeconfig 需要提前在 Jenkins 裡配置），使用 helm 部署或者更新應用。

 之前的流水線都是聲明式的，通過 script 來冩一些腳本，這次乾脆直接使用腳本式；在這個項目中實際包含了兩個應用，也用到了循環分別進到不同的目錄構建和部署（需要和研發溝通）；除此之外，之前都是明確分支或者標籤的，所以在一開始冩了個 GIT_BRANCH 或者 GIT_BRANCH_TAG 的變量，而在這個流水線里拉取的分支變量是 target ，考慮到和觸發器有關就在 Jenkins 的頁面上配置了：這裡的邏輯是 rc 分支部署到測試環境供測試人員測試，develop 分支部署到開發環境供開發人員自測，而 develop 是可能有多個研發完成不同特性分支 merge 上去的，這個單獨的特性分支 push 之後，也會通過 helm 部署一個特性的 release 應用以供研發自測特性功能。

  還需說明的一點是，個人認為流水線一般只負責到更新就完成了，至於更新是否成功或者如果失敗是否需要回滾，可能需要研發排查代碼或者運維排查配置其他問題，沒有必要包含在流水線內。

  可以看到本人在不同階段的流水線中用了很多插件，實際上對於 DevOps 工具而言，應該儘可能只使用它最核心的功能。插件是有學習成本的，增加了閱讀和編冩難度的同時，也可能導致其他問題：比如最後一個案例中所有編譯和構建都在 pod 中，雖然提高了隔離性，但不管是前端還是後端的依賴都需要重新拉取，影響了構建速度，如果再使用 hostpath 掛載目錄，就需要考慮固定某一節點，這樣反而複雜了。
  業務繁多，任何流水線都有優化的空間。說句有用的廢話，適合自己的才是最好的。
