K8s 常用 yaml 彙總

更新於2023-03-13|ops
|字數統計:6.6k|閱讀時間:37分鐘|瀏覽量:

  由於工作需要，K8s 總有服務是需要重複部署的，例如監控、日誌等，每此都從網上整理很麻煩，而且往往有錯誤或者因 K8s 版本原因需要修改。雖然使用 helm 或者 operator 方式部署更為方便，但都是經過別人封裝的東西，且萬變不離 yaml。

說明

  1. 涉及到的數據存儲都依賴於 StorageClass ，需要 K8s 集群內提前創建。
  2. 使用的鏡像如不加 tag ，即使用 latest 鏡像，以供使用者有需要添加制定版本的 tag。
  3. 個人習慣創建資源的順序為 RBAC → Configmap/Secret → Deployment/Statefulset/Deamonset → Service ，實際可按需使用 Ingress。（看到文章說 svc 先於 deploy 等工作負載創建會比較好，個人覺得從邏輯上 svc 的端口是從工作負載裡聲明的，沒有工作負載也沒有對應的 svc）

Thanos

 本文采用 sidecar 模式，把 prometheus 和 sider 服務部署在一起，query 服務提供跟 prometheus 一樣的查詢界面，store 服務儲存到 minio，compact 服務壓縮數據文件，因為 prometheus 已經配置 rule 告警規則，故 thanos 的 rules 服務不在部署，僅供參考。（如果部署 rules 的話，可以在 query 界面中既包含 prometheus 本身的告警規則，也可以看到 rules 服務的規則），詳情參考 Thanos-io/kube-thanso

01-prometheus-rbac.yaml

 和 prometheus 的 rbac 保持一致即可

02-prometheus-tp-cm.yaml

 可以由稍後的 05-prometheus-sidecar-sts.yaml 看出，prometheus 僅提供 後綴為tmpl的模版配置文件 由 sidecar 解析後生成 後綴為yaml的標準配置文件 ，所以此 configmap 只是文件名不同，配置項也和 prometheus 的一致。

03-prometheus-rules-cm.yaml
