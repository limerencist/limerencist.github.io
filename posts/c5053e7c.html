我的機器人也上雲啦！

更新於2026-06-09|ops
|字數統計:2k|閱讀時間:7分鐘|瀏覽量:

  根據前文已知，最近工作的重心就是在和 Telegram 的機器人打交道，之前都是本地開發測試，現在領導又有要求將其部署到服務器上。看起來差距不大，實際操作還是有些不同。

本地 Ngrok

  在身邊大佬的框架下，本地開發使用的是 ngrok 的方式進行內網穿透，整個過程基本如下：

  1. 註冊 ngrok 申請免費測試的域名；
  2. 安裝並啟動 ngrok，配置代理 （以下命令會在 ngrok 的管理頁面可直接複製）；
  1. 修改配置文件，我的程序中需要這個域名 + 接口路徑作為回調地址，不需要的話可以跳過；
  2. 本地啟動服務，比如端口是 8888；
  3. 測試是否成功，比如是否能通過域名訪問 swagger 頁面或健康檢查接口；

  整個流程很是絲滑，沒有痛點，即使是小白成功操作的幾率也很高。如果碰到問題，可以訪問官網文檔Get Started with ngrok - ngrok documentation，或者參考知乎的 # 利用ngrok實現內網穿透（全網最詳細教程）。

 PS：其實一開始我並沒有想通為什麼需要使用 ngrok 內網穿透，畢竟我本地程序可以接受並回復 Telegram 的消息。後來我想到，可能之前的程序比較簡單，隨意使用任何 API，限制沒有那麼多；現在集成到大的框架裡面，涉及到與 TG 的內外互通。

  • 通過 ping 或者 nslookup 命令查看域名是否解析成功 ✅

webhook 未配置

  在反覆比對雲上和本地環境之後（肯定不是代碼的問題，畢竟 go 語言編譯的可執行文件哪都通——用），發現失敗的第一個原因是沒有配置雲上服務的 webhook，現在的 webhook 還是我本地使用 ngrok 的地址，而且，也不能同時配置多個 webhook。結果，重新配置 webhook 後依舊不行。

GCP 安全組

  根據查看 getWebhookInfo 接口返回的結果來看，telegram 與我方服務始終連接超時，也就是往外面的請求進不來，而我本地又可以訪問 swagger 頁面，打開手機使用移動網絡訪問 swagger 卻無法連接——答案便呼之欲出：雲上的安全組問題！一定是白名單隻允許公司 IP 訪問，來自 telegram 的請求則被攔截！查詢相關資料後，telegram 也確實提供需要添加白名單的 IP 段。本以為添加之後可以順利，沒想到還是不行，安全起見我又不能直接開放 0.0.0.0 先測試再過濾，進展一度停滯不前！雖然大概率是這個原因，但畢竟無法驗證。

分析

特性Nginx 反向代理 (傳統模式)Cloudflare Tunnel (隧道模式)
流量方向**入站 (Ingress)**：流量從外部主動撞擊你的服務器**出站 (Egress)**：服務器主動向 CF 建立加密長連接
防火牆要求必須在 GCP 和系統防火牆開放 80/443 端口無需開放任何入站端口，只要服務器能上外網就行
IP 依賴Telegram 直接連接公網 IPTelegram 連接CF 節點，流量走內部隧道到達服務器
網絡環境容易受 NAT / 動態 IP 或複雜的雲廠商安全組限制無視 NAT 和複雜網絡，哪怕沒有公網 IP 也能用

 從以上的表中就可以看出，AI 確實適合做總結，廢話不多，句句都在關鍵點：相比較 Nginx 的被動等待，Cloudflare Tunnel 選擇主動出擊，同時繞開雲服務商上的種種限制，簡單有效，一舉定乾坤！
