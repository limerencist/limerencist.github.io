Steam 遊戲，買國區還是日區？

更新於2026-06-09|plus
|字數統計:3.4k|閱讀時間:13分鐘|瀏覽量:

  不知不覺，6月已經到來。除了兒童節預示著夏季的到來，每年的 618 活動也早已在 5月底就開始上線。而對於等等黨而言，6月份真正重要的，還得是月底開啟的 Steam 夏季特賣活動。

  今時不同往日，以前只能在國區買遊戲，而且動不動就鎖區下架；現在好了，我可以換成日區看看，雖然從定價上來說，國區的總體價格會更便宜一些，但凡事總有例外，說不定有相反的結果——就算沒有，也至少不會鎖區，而且還能用日本的 Steam 充值卡。

  轉區其實不麻煩，隨便買個遊戲，支付之後選擇對應貨幣就行，前提是有日本的支付方式。比較蛋疼的是，當天買完沒事，第二天 Steam 懷疑我被盜號，不僅直接取消我的訂單，而且還要我回復客服驗證。哎，明明是很正常的操作，結果還被懷疑盜號，真是無語。一陣罵娘之後，我只好硬著頭皮回覆客服，結果不知不覺直接重置了 Steam 密碼，又是一通操作，略下不表……終於折騰完了，直接看看日區的 Steam 遊戲價格。因為我之前是按價格排序的，現在重新排序之後，明顯看到遊戲位置的變化；再搜搜鎖區的遊戲，果然有，一切便了然於胸。現在的問題在於，無法直接比較國區和日區的價格，而且就算能同時看到不同的價格，中間還隔著匯率。既然人工做不了，那就交給程序去做，由此開啟了將要介紹的 python 之旅。

  查閱一翻資料後發現，Steam 確實提供了公開的查詢接口用於獲取遊戲的詳細信息，前提是需要提供遊戲的 ID，而每個遊戲的 url 裡都包含了這個 ID。但我總不能從願望單裡打開每一個遊戲，然後再手動複製吧，肯定有更簡單的方法——喏，這不就來了嗎？https://store.steampowered.com/dynamicstore/userdata/。這個接口直接在瀏覽器裡就能打開，結果是很多 JSON 數據，不過都是空值；如果已經登錄過 Steam 的話，就會返回正確的數據。需要關心的，是第一位置的 rgWishlist，裡面存儲著願望單裡的所有遊戲 ID。既然準備工作完成，接下來就能交給程序了。老規矩，不急著寫代碼，整理下思路：

  1. 獲取 json 中願望單遊戲 ID；
  2. 根據遊戲 ID 獲取遊戲的詳細信息，篩選所需的必要字段；
  3. 比較國區和日區的價格，通過匯率，統一貨幣單位；
  4. 輸出結果，彙總到表格中。

  這麼想的話，其實並不複雜，然而實際操作起來，卻多了意想不到的步驟，過程也逐漸曲折。現在拿著現成的代碼去回述整個過程，也不由地感慨萬千。

main

  上面的 userdata 接口在於獲取遊戲 ID，一般來說不需要經常操作。這裡就把瀏覽器請求的結果保存到 json 文件中，通過程序讀取即可——順便排個序，然後拿著 ID 獲取我想要的信息，最後寫入表格。

get_cny_to_jpy_rate

  這個目的就很明確了，獲取人民幣對日元的匯率，用於後續的價格轉換。當然也可以反過來獲取日元對人民幣的匯率，只要最後的貨幣單位統一就行——主要是日元的價格數字看著太大，心理壓力陡增，還是人民幣看著舒服。同時接口比較簡單，就沒寫複雜的 try 處理請求異常的情況。

request_game

  如上文所述，請求遊戲信息，需要傳入遊戲 ID；考慮到需要國區和日區，再多加一個國家代碼的參數；默的 "l":"schinese"則是保證返回中文名稱，不然看英文名我也不知道哪個是哪個；UA_LISTS 用於隨機選擇 User-Agent，避免被反爬蟲機制識別；有關於 data 的處理，可以直接在瀏覽器發送請求返回的 json 數據，然後進行提取：

  1. 正常情況，返回 名稱/價格/折扣，也就是 name, price["final"] / 100, price["discount_percent"]；
  2. 有 ID 查到遊戲信息，但是沒有價格字段，說明未發售，返回 name, -1, 0；
  3. 有 ID 卻沒有返回數據，說明該遊戲鎖區域，則返回 "", -2, 0；
  4. 如果是請求本身有問題，就打印出遊戲的 ID，好知道哪個遊戲請求失敗了，同時 返回 "", ERROR_CODE, 0；

get_game_list

  這個函數是在 main 函數裡直接調用，可以說整塊業務的核心，有著 承上啟下 的作用。當初寫的時候，也是反覆修改最多的地方。原本的目的是為了根據 ID，一個一個查詢並組成我想要的信息，也就是 game_data：包含 ID、名稱、日區價格、折扣、日區價格摺合人民幣、人民幣價格、價格差值、購買建議；而且，正常情況也就是中日都能查到價格，才能進行比較；否則就根據返回的代碼，通過 STATUS_MAP 來賦值；國區鎖了，不用比，肯定是買日區；沒發售，也不用比，肯定是沒得買；可以看出，原本返回價格的佔位字段，為了減少變量和代碼複雜度，不僅僅只是價格而已。組裝完成後，使用 total_game_list 返回完整的遊戲信息列表。

  最難的還不是這個，而是 Steam 對於請求的反爬蟲機制。實際編寫代碼的過程中，剛開始只用了幾個 ID 測試代碼功能，並沒有什麼問題；可後面用完整的數據測試時，我發現如果一下子請求次數太多，除了開始請求的部分 ID，後面的 ID 完全獲取不到數據，返回的都是錯誤代碼。

  為此，才會在上面定義 header 的時候，使用了隨機的 User-Agent 來模擬不同的瀏覽器，減少被識別為爬蟲的概率；除此之外，再通過 BATCH_SIZE 和 WAIT_TIME 來限制請求次數和增加請求間隔。因為需要請求 2 個區域的價格，所以總請求數是實際數量的 2 倍。可如此一來，從發送請求到最初結果產生，這之前的間隔也會隨著請求的數量和延時時間而變長，也無法確認，這期間程序是否仍在正常執行，又或者請求結果中包含異常的數據。

  既然已經 game_list 用於存儲最後寫入表格的數據，那不妨增加一個臨時的 game_list 來存儲當前批次的數據。一旦觸發了請求限制的機制，就把當前獲取到的數據先打印出來：既能證明程序還在正常運行，同時還增強了類似於進度條的既視感，能夠對程序的結果有所掌握，這才有了 current_game_list 和打印其到終端的 console_table 函數。需要注意的，每次打印完當前批次的數據後，都要清空 current_game_list，來保證每次打印的都是最新的數據。

console_table

  終端打印表格的話，為了美觀，需要使用 prettytable 庫來格式化輸出。從代碼量上看，使用的方法也不復雜。唯一增加的地方，就是 table_counter 這個全局計數器來顯示行號，也就是查詢到的有效數據的數量。如果不加這個，對程序本身的邏輯並沒有影響，只是純粹看錶格的時候不夠直觀，畢竟 excel 的話，會自帶這個行號。

write_excel

  終於到最後一步啦！在排除萬難之後，現在獲取到的數據已經很完善了，接下來就是寫入到 excel 文件中。結合 pandas 和 openpyxl ，來操作表格文件。和 prettytable 一樣，本身使用並不複雜，幾行代碼就能搞定。不過，為了最後輸出的結果更明顯，加了點上色的需求。

結果展示

  來吧，見證奇蹟的時刻到了，看看這個程序的執行過程和最終成果吧！

  使用 logging 打印時間的原因，就是方便查看程序執行的時間，以及統計每一步的耗時。區區 69 個遊戲的數據，居然花了 4 分半左右!（準確來說是4m26s860ms，你猜我怎麼知道？之前介紹的 starship 可不是白配置的）當然，可以看出其中等待的時間佔據了絕大多數。姑且算一下，每 30 個請求也就是 15 個遊戲，分 5 次完成，其中 4 次都會觸發防止反爬蟲的延時機制，這就已經 4 分鐘了！不過，這也說明程序的執行，符合代碼的預期。而且從結果上來說，還是相當不錯的。除了購買建議和折扣力度之外，Diff 字段一下子就能看出同一個遊戲在不同地區的價格差異：絕大多數情況下，國區價格確實要比日區便宜不少，即使現在日元在貶值的道路上一去不返，日區某些遊戲的價格也還是貴得離譜！
