完蛋！我被價格包圍了！

更新於2026-06-09|plus
|字數統計:3.2k|閱讀時間:12分鐘|瀏覽量:

  上次已經通過 Steam 的公共 API 獲取了願望單中不同地區的價格信息，但是平日都要貨比三家，真正的老司機又怎麼可能只在 Steam 買遊戲呢？別的不說，光是 Epic Games Store 憑藉其人見人愛的“喜加一”特色活動，也擁有一大批忠實用戶。雖然遊戲數量不如 Steam 那麼豐富，至少在價格上也有參考的價值。

  不過，如果像 Steam 那樣，通過公共 API 來獲取 Epic 的價格信息，則稍微麻煩一點。查閱資料後，不如直接調用三方平臺的 API 來獲取價格信息，這就輪到 IsThereAnyDeal (ITAD) 出場了。直接通過 Steam 賬號綁定 ITAD，就可以獲取到位於右下角的 API Key。記住這個 Key，代碼全靠它。

  因為大體的流程其實和上次差不多，我原以為代碼會很相似，結果查詢了下 ITAD 的 API 文檔之後，發現還是要做不少改動。主要有以下幾點：

  1. 同樣是需要遊戲 ID，但是 ITAD 的遊戲 ID 和 Steam 的遊戲 ID 不同，雖然也有接口可以直接用 Steam 的遊戲 ID 來查詢遊戲，但是為了獲取更全面的信息，還是需要先做一次轉換，畢竟 Steam 的遊戲 ID 已經是現成的，即使再次獲取也不麻煩，而獲取 ITAD 的遊戲 ID 則沒有那麼輕鬆；
  2. 通過遊戲 ID ，Steam 一次請求可以獲取到遊戲的詳細信息，包括價格；但是 ITAD 需要分別請求多個接口來獲取這些信息，遊戲是遊戲，價格歸價格；
  3. 還記得上次的限流阻斷延時嗎？一個 ID 一次請求，請求稍微多一點，Steam 就會觸發反爬蟲機制；ITAD 就不一樣了，一次就可以發送多個 ID，請求量驟減，完美規避了限流問題。

main

  如此，結合上一次的經驗，主函數的步驟如下：

  1. 根據已有的 Steam 遊戲 ID，先轉成 ITAD 的遊戲 ID（一次請求，批量獲取）；
  2. 根據 ITAD 的遊戲 ID，通知獲取 Steam 和 Epic 的價格信息（同樣也是一次請求，批量獲取）；
  3. 抽取價格中需要的信息，比如歷史最低、Steam 價格、Epic 價格等；
  4. 這一步做不做看個人實際的需求：雖然 ITAD 提供了遊戲信息的接口，但是隻有英文名，對於我這種中文玩家來說，肯定是不夠直觀的，所以還是需要再調用一次 Steam 的遊戲信息接口獲取中文名；如果不介意英文名，可以直接調用 ITAD 接口，畢竟量大管飽沒限制；當然，考慮到最終結果是保存到文件裡的，況且已經按照 ID 排序，上一次也獲取到了遊戲的名稱，剩下的其實直接在 Excel 操作裡複製粘貼就行，完全省略這一步；
  5. 數據大整合，終端表格或者文件輸出；

get_itadid_by_steamid

  基本上還是一個普通的 POST 請求，稍微說下不同的地方：

  1. 文檔說明可以在請求的 header 中直接添加 ITAD_API_KEY 這個字段；
  2. STEAM_LOOKUP_API 的接口中需要 steam 的 shopId，可以通過 https://api.isthereanydeal.com/service/shops/v1 獲取；
  3. 並不是直接傳入 steam_id 就行，需要 app/{steam_id} 的格式，一次可以傳多個 steam_id，從而獲取批量數據；
  4. 從變量的命名就可以看出，返回的結果是 steam_id: itad_id 的字典，用於最後彙總數據時使用；

get_price_by_itad_id

  同上，差異不大，只是請求的接口和參數不同而已。不過曾經我也以為沒有限制，後來發現其實我的傳入的數據不夠多。當一次性傳入超過 200 個 itad_id 後，接口便返回了錯誤信息——也可以理解，畢竟返回的結果卻是很多。因此需要分批處理，再把所有的結果彙總。注意的是，這裡通過 extend 而不是常用的 append 來添加，否則後面的解析會出問題。

filter_price

  到上面為止，對 ITAD 的數據請求基本已經完成了，接著就是對數據進行過濾和整理。其實這一部分也可以在上一步中完成，不過我還是覺得把數據的請求和處理分開比較好，邏輯上更清晰一些。實際上只需要 史低價、steam 價、epic 價即可，額外獲取 steam 和 epic 的折扣信息，原價就不要了，避免數據太多看得太亂。返回的是 itad_id 和對應的價格信息的映射字典。

get_game_by_itad_id

  剛才說這一步如果需要獲取遊戲中文名的話，仍然需要調用 steam 的接口。因為已經在上一期寫過對應代碼，這裡就不提供了；由於下一步需要獲取遊戲的其他信息，這裡還是請求一下 ITAD 的接口；跟之前的接口不一樣，這個接口無法批量請求多個 ID，只能一個一個請求。不過後續使用場景有限，也不用過分在意。

join_steam_and_itad

  這一步就是把上面獲取到的數據整合起來，形成最終的結果。現在到手的數據是：

  1. steamid_to_itadid：Steam 遊戲 ID 到 ITAD 遊戲 ID 的映射；
  2. itadid_prices_map：ITAD 遊戲 ID 到價格信息的映射；
  3. steam_name_map：Steam 遊戲 ID 到遊戲名稱的映射（根據情況也可能是 ITAD 遊戲 ID 到遊戲名稱的映射，或者不需要）；

  看起來是不是有點像數據庫的關聯查詢？如果是數據庫的話，這一部分直接一個 SQL 就能搞定；可惜，這裡只能手動實現。以 steam_name_map 為基準，遍歷其中的每個遊戲 ID，通過 steamid_to_itadid 找到對應的 itad_id，然後在 itadid_prices_map 中查找對應的價格信息。由於都是 map，所以查詢很快。如果 itadid_prices_map 中存在對應的 itad_id，說明是有價格信息的，然後再獲取具體的價格和折扣信息；反之沒有的話，可能鎖區或者下架或者未發售，臨時加的需求就是通過上一步的 get_game_by_itad_id 看看有沒有發售時間。不加也沒事，看個人需求。

問題

  剩下的終端表格展示和寫入excel文件的代碼，和上次的差別不大，就不重複貼了。反正只要數據有了，怎麼展示都是小問題——還是先看下運行效果吧！

  細心如我肯定發現有漏洞：鼎鼎大名的國產遊戲《太吾繪卷》，居然沒有查到價格，而且不止一個遊戲有這個問題，這一看就不合理！連忙去 ITAD 官網查了下，頁面上價格、區域啥的都有。我又看了看程序，沒啥問題啊，95%的請求都成功了，怎麼就這幾個不行呢？真是百思不得其解！重新結合數據、頁面重新分析了問題後，確實被我發現了其中的貓膩！

  首先，頁面上能查到，則說明這個遊戲肯定在 ITAD 上有記錄；其次，上面說過，所有數據都是通過遊戲 ID 獲取的，放在程序中的話，也就是 steam.json 中的 steam 遊戲 ID，進過一次轉換，變成了 itad_id；現在程序裡查不到，說明用的 itad_id 不對；那我怎麼知道頁面能查到的遊戲對應的 itad_id 呢？

  貼心的 ITAD 提供了 https://api.isthereanydeal.com/lookup/id/title/v1 的接口：於是我直接用這個接口查詢了 太吾繪卷 The Scroll Of Taiwu 這個完整的遊戲名稱，返回結果中的 itad_id 果然和通過 steam_id 轉換得到的 itad_id 不同！我又試了試 The Scroll Of Taiwu……來人，上證據！

  真相大白！因為遊戲改過名！

  在 Steam 中，管你是 The Scroll Of Taiwu 還是 太吾繪卷 The Scroll Of Taiwu，反正都是同一個 ID，名稱改了而已；而在 ITAD 中，這被認為是新舊兩個不同的遊戲，拿舊的 itad_id 去查，自然就查不到了。我又試了試其他的遊戲，果然也是同樣的問題。

  知道問題所在我就放心了，但要在程序裡解決這個問題，則比較麻煩，最主要的是我無法批量獲取到正確的 ITAD 遊戲 ID。如果我用名字去查，還得先通過 Steam 接口獲取到遊戲名稱，還得是英文名，然後再查遊戲 ID，最後查遊戲價格，我覺得操作上覆雜了。況且，絕大多數的數據還是有的，針對少部分的這幾個遊戲，頁面上看看也無妨。另外，這次也不同時獲取中日的價格了，反正改個 COUNTRY_CODE 就行，兩張表通過 Excel 合併價格信息。不然，同時要獲取 10 個價格，那可真真被價格包圍了！
