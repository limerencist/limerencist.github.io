Golang 之 kubebuilder

更新於2026-06-09|dev
|字數統計:4.7k|閱讀時間:20分鐘|瀏覽量:

 好久沒攢大活了：別急，大招需要 CD 的，憋一憋才能放。既上次通過 client-go 操作 Deployment、Service 之後，這次我把目標瞄向了 CRD ——自定義資源。換個方式想，Deployment、Service 這些是不是也算 K8s 早期的自定義資源呢？試過之後就知道。

準備工作

podman

  • 下載 podman 後配置鏡像庫地址 /etc/containers/registries.conf
  • 搭建鏡像私庫

kind

  • 下載 kind 後編輯 kind.yaml
  • 為方便通過 kubeconfig 訪問 K8s，建議文件裡冩下具體 IP，否則默認 127.0.0.1：當然，不加也沒關係，反正都是本地開發調試。

k9s

  • 強大的終端 K8s 管理神器，直接官網下載就能用

kuboard

  • 簡單快速的 K8s Dashboard，v3 和 v4 版本差異比較大，建議使用 v3 版本( v4 不僅需要額外的數據庫，而且修改 v3 按照 Namespace 操作的習慣，改為按 Controller 操作)
  • podman 拉起後訪問 http://ip/login ，使用 admin/Kuboard123 登錄，修改密碼後再次登錄

  注意：以上容器都是通過 podman 拉起的，但 podman 沒有守護進程，所以機器重啟之後，即使創建容器時添加 --restart 容器並不會自動啟動，需要使用命令手動啟動；或者通過 podman generate systemd 來實現自起。

 至此，準備工作完成，下一步開始開發 operator ！

工具選擇

  一番百度之後，瞭解到開發 operator 的框架主要有
operator-sdk，kubebuilder 和 Kudo 等。這三個我都去試了一下，簡單說下初步使用的感受：

  1. 剛開始用的是 Kudo：手頭正好有一份使用的簡介資料，而且瞭解到它是聲明式的，不需要冩多少代碼，基本上 yaml 和 shell 就可以完成，算是對新手比較友好。可是，實際使用的時候，發現它的 GitHub，最近 1 次更新已經是四年前，而且它的 api version 和現在的 k8s 版本已經有明顯的不兼容，只好悻悻作罷；
  2. 其實是 operator-sdk:它除了支持 go 語言開發外，還支持 ansible 和 helm（是不是以為我這裡會說 _還支持 python、java 等開發語言_）。後面兩個對運維人員來說可以說是老朋友了：考慮到 helm 基本上就是 yaml 文件的集合，同樣不涉及代碼開發，先用這個試了試水。試過之後跟著官網文檔走就行了，基本上沒啥問題，感覺也沒有記錄的必要；
  3. 最後是 kubebuilder：用這玩意兒就基本是衝著冩代碼去的，就和 operator-sdk 裡 go 方式基本一樣（官網例子裡有些鏈接還直接指向了 kubebuilder）。反正都要冩代碼，那就索性用它了。

初始化項目

  安裝步驟不必多說，直接跳過，無非是 go get 那些，咱直接初始化項目：

  創建時候需要輸入 2 次 y 來自動生成相應的文件，後續主要在這裡面冩代碼。

  分析下主要目錄結構：

  • api/: 剛定義的 api，描述自定義資源
  • bin/: 執行、編譯、打包等操作需要用到的可執行文件
  • cmd/main.go: 主程序入口
  • config/: 存放需要的 yaml 文件
  • internal/controller: 控制程序代碼
  • Dockerfile：構建鏡像
  • Makefile: 執行、編譯、打包等操作的自動化命令

api/v1/mygin_types.go

   xxx_types.go 文件是剛才自動生成的文件之一，看名字就可以看出這個文件的作用是定義類型——什麼意思？不妨先打開一下看看默認有啥。

  這裡先把註釋去掉了，能看著個清楚一些：是不是很熟悉？和之前 client-go 獲取 Deployment 那些東西很像。如果 把 MyGin 替換成 Deployment 的話……

 MyGin 就是 CRD，雖然是自定義的，但也要符合 K8s 裡資源的規範，就需要有：

  • TypeMeta 說明定義的是個啥玩意兒：是 Deployment ，不是 StatefulSet；
  • ObjectMeta 說明具體的東西：現在已經是 Deployment 了 ，是哪個空間下的叫啥名呢；
  • Spec 說出你的期望：想要這個 Deployment 是啥樣子的；
  • Status 實際的狀態：期望之後，究竟結果如何呢；

  現在想一想當年 chua chua chua 冩的 yaml 裡不就是這麼些個東西嗎？ Status 是不用冩，Spec 那真叫一個痛不欲生。

  既然知道這裡需要什麼，就可以開始填空：

  我這裡簡單定義 Size(也就是副本數)、Image ，同時加 1 個校驗。這裡尤為需要注意的是 **json:"size,omitempty"**：這會影響自定義資源 yaml 裡的字段信息。

  Status 加 3 條，輸出些信息，意思意思。

internal/controller/mygin_controller.go

   xxx_controller.go 文件自然也是剛才自動生成的文件之一(這句好像是廢話了)，有關協調、控制過程的代碼都可以冩在這裡。

RBAC

  開始就是很重要的的東西！很明顯是 RBAC，但這只是對自定義資源。這次是要操作 Deployment 和 Service，獲取 Endpointslice 信息，都得加上。

  第一次我就沒加這些東西導致 operator 程序啟動報錯，幸好日誌裡看到。

創建關聯控制器

  這些代碼都不算很核心，看名稱就知道作用：就是填充 Deployment 和 Service 裡的字段，和一般不同的是我冩了 2 個容器： nginx 固定鏡像和端口，勉為其難臨時充當一下前端；mygin 端口也固定 9000，鏡像信息交給 CRD 裡 Spec 的 Image 字段；

  初始化的過程看字段信息和 yaml 裡都是一致的，唯獨 Service 裡的 TargetPort : 居然是 intstr.IntOrString{IntVal: 9000, StrVal: "mygin"}!

  另一個注意點就是 SetControllerReference，用於建立關聯後，刪除自定義資源時就會將 Deployment 或者 Service 也刪除掉。

協調過程

  以上部分的代碼就是整個 controller 協調的過程，我把它分成 3 部分：

  1. 找實例，找不到則創建：
  2. 調整 mygin 實例的副本大小（雖然 mygin 實例裡確實通過 deployment 去呈現，但始終需要記住的是：我們改的是 mygin 的副本數，再交由 controller 去協調整個改變的過程，這一點下面還會再說）
  3. 更新 mygin 實例的 Status 狀態

  怎麼去判斷 mygin 實例的狀態是好是壞呢？鑑於 mygin 實例需要創建 Deployment 和 Service，判斷也應由此入手。

  前者很好判斷：Deployment 裡本身就有 Status 信息的反饋，如果發現可用副本數 ReadyReplicas 和預期定義的 副本數 myGin.Spec.Size 一致，那應該就行；可是 Service 呢？它的 Status 只有 loadBalancer，大多數情況下還為空。

  想到 Service 的後端是 Endpoint，這裡可以作為判斷的依據，結果提示 Warning: v1 Endpoints is deprecated in v1.33+; use discovery.k8s.io/v1 EndpointSlice，也就是 Endpoints 過期，建議用 EndpointSlice。剛開始冩的代碼雖然也能用，但是有問題咱就解決，將操作對象由 Endpoints 改為 EndpointSlice，然後發現——不行了。

  問題就在於：Endpoints 和 Serivice 的名字是一致的，之前都是通過這個 Name 去找對應的資源;而 EndpointSlice 就比較有個性，跟 ReplicaSets 一樣，會在 Name 後面加隨機字符串：這就導致原來的方法走不通，所以上面的代碼裡才會兜了一圈根據標籤去找，然後根據 EndpointSlice 裡面狀態為 Ready 的 Addresses 數量做判斷。

   SetupWithManager 方法是自動創建的時候默認就有的，添加 Owns 是告訴 Manager ：這個 CRD 有依賴的 K8s 控制器，如果他們的 Spec 或者 Status 發生改變，要重新觸發 Reconcile 的協調過程，也就是千辛萬苦冩的代碼。

 修改完代碼後一定要記得 make manifests 一下！！！

效果展示

 代碼冩完之後需要部署，正常來講都是通過 yaml 或者 helm-chart 包，為了方便調試，先不這麼做，而是通過 make install。

make install

  • 執行 make install run 本地部署並調試

  • kuboard 和 k9s (二選一)查看是否有 CRD

  • 創建 MyGin 實例

  在 config/samples 目錄自動生成的 webapp_v1_mygin.yaml 文件 裡可以看到裡面已經填充了一些字段，name: mygin-sample 說明該實例的名字，除此之外手動添加 namespace、_Size_、image 信息


  可以看到有錯誤，剛才故意把 size 的 S 大冩就是為了這裡——上文說的代碼會影響填冩字段；同時發現，代碼里加的驗證也生效了。

  • 修改正確的字段和值，再 kubectl apply 查看結果

  最直觀的效果是可以看到成功創建 Deployment 和 Service ，但這只是 MyGin 這個 CRD 的表現形式，是更為關鍵的是，我們需要看到是否剛才定義的 mygin-sample 實例。

  k9s 看到創建的 MyGin 實例和 yaml 裡定義的一致，Status 顯示也很非常。

  • 更新副本和鏡像


  試著調整 Deployment 的副本數，發現無法修改。


  而更新鏡像，卻沒有問題。

  不過因為拉取不到鏡像，所以 Status 異常。

  原因很簡單——因為我沒冩！回看上面代碼的話，就會發現只對副本數進行了控制。

  日誌說明問題！這個問題待會修復。

  • 刪除卸載

  最後通過 kubectl delete 刪除 MyGin 實例，make uninstall 卸載 CRD 。

make deploy

 剛才用 make install 看到 CRD 的 controller 程序是部署在集群外的，是為了方便調試；代碼如果需要定版發佈，那就可以構建鏡像生成 yaml 並且將程序部署在 k8s 內部，也就是正常應該使用的方式。

  • 添加調整鏡像的代碼

 修改完代碼後一定要記得 make manifests 一下！！！

  • 修改 Makefile

  刪除默認的 IMG ?= controller:latest
  添加 IMG ?= 192.168.10.11:5000/mygin-operator:1.0.0

  • 修改 Dockerfile

  配置 GOPROXY 加速相應庫的拉取；修改默認的源鏡像為 alpine （這個純屬個人習慣）；
  如果不想在多階段構建裡重新拉包，也可以直接先本地編譯好，然後把可執行文件放到 alpine 源鏡像裡也行，畢竟默認的 golang:1.24 鏡像也挺大的；

  • 執行 make docker-build docker-push 構建並推送鏡像

  整個過程的時間主要取決於 拉包 和 編譯，編譯這個沒辦法，只能看機器給不給力；但是如果沒有在 dockerfile 裡配置加速，這個時間會讓你懷疑人生……

  看過程的話其實就是生成 yaml 文件再執行

  正常情況下就會在 xxx-system 的命名空間下創建 operator 程序的 Deployment
