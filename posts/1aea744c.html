Golang 之 swagger

更新於2025-07-11|dev
|字數統計:1.7k|閱讀時間:6分鐘|瀏覽量:

  以前部署公司服務的時候，經常會打開 swagger 頁面：一來是可以驗證服務正常，相當於 1 次手動的就緒探針；二來，有些簡單接口直接就可以在頁面上做調試，不用再打開 postman 或者 apifox，當時覺得這東西真不錯。

  第一步自然是面向互聯網。跟著網上的教程基本上就能搞個七七八八，我這裡就是記錄一下。

  這兩個例子雖然簡單，但其實真的要細講也要費一些篇幅，我建議是依葫蘆畫瓢自己多試試——因為我自己都是根據網頁上的教程試了半天，才稍微有些理解。

  比如說：我在 ping 接口加了一條 // @Success 200 {object} response.Result的註解，所以 swagger 頁面上 ping 接口就多了 Responses 200 的內容，而這個 response.Result 是我自定義的結構體，

  又比如說，我在 helloform 接口加了兩條 // @Param name formData string true "Name" // @Param age formData int true "Age"，因此 swagger 頁面上就出現了該接口需要的參數和數據類型。

回到開頭

  還記得該開始說的 swag init 和自動創建的文件嗎？其實，只要給代碼加上註解，都需要執行 swag init。考慮到文件裡的內容太多，就直接截取部分，可以自己看下文件裡的內容是不是和頁面上看到的一致（json 和 yaml 文件裡關於 swagger 的內容是一致的，只是展現形式不一樣）

困擾我的問題

  最近冩 swagger 的時候，有一個問題困擾了我好久，就是 BasePath。我的路由代碼是這樣的：

  接口訪問的路徑是 /api/v1/user/xxxx，於是註解自然而然就這麼冩了：

  這樣的話，swagger 頁面顯示的也是 /api/v1/user/login

  然後問題就來了，通過頁面請求發現地址變成了 /api/v1/api/v1/user/login

  後來我才理解 BasePath 就是會在頁面看到路徑前面自動拼接的路徑：如果完整路徑是 /api/v1/user/login，那麼註解裡就不用再重複冩 /api/v1/。不然，把 BasePath 冩成 /，也 OK，只要清楚真正的路徑是什麼就行。
