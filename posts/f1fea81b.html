那你的機器人能識別語音嗎？

更新於2026-05-22|devops
|字數統計:2.1k|閱讀時間:7分鐘|瀏覽量:

  舊的問題剛剛解決，新的需求接踵而來：這次要識別語音消息，並且將結果的文本進行關鍵詞匹配。

文本匹配關鍵詞

  考慮到後者比較簡單，就先實現了：

  這明顯，這個方法 2 個參數：一個是需要匹配的內容 content，另一個是匹配的規則 rules。程序上沒有什麼好說的，值得一提的是其中比較微妙的邏輯視角：是按照 rules 去匹配 conent？還是拿著 content 去問 rules？

  從匹配的結果上，好像沒有什麼區別。但是，如果是前者的話，當匹配不通過時，並不知道是哪個地方出的問題；而後者，則能 診斷 出結果；當然，也不需要一直匹配到最後，只要有不符合的，就提前退出熔斷，避免增加時間複雜度。

  起初我想的只是把 content 轉換成小冩再進行匹配，在後續的 AI 建議中，幫我優化成現在的結果：過濾文本中無需關心的特殊字符，我覺得這樣更科學一點。

語音識別

  這個稍微麻煩一點，雖然一開始就知道肯定是要調用第三方語音識別庫的，但是調用和調試的過程，那可真是完全沒有接觸過——好在現在有 AI ！在 AI 的輔助下，完整的代碼就有了——先別急，慢慢解析（在冩代碼之前記得先安裝 ffmpeg 哦，語音必備工具）：

模型框架

  現在看這個大框架都那麼幾行，其實光 import mlx_whisper 和 MODEL_PATH = "mlx-community/whisper-turbo" 這兩行就花了好長時間才確定下來。本來選用的是 Fast-Whisper，結果在我的 MacBook 上通過 pip3 安裝時候始終有問題，於是改成openai-whisper；簡單測試後，才最終使用 AI 建議該用針對 M芯片有優化的 mlx_whisper；其次，在模型選擇上也有取捨，這邊就簡單上結論：whisper-turbo 短小精幹，whisper-large-v3-mlx-4bit 強大精確，結合自己的環境和需求選擇就行。

文本匹配

  這段代碼就很眼熟了，就是開頭 go語言的翻版，可以看出 python 代碼的簡介之道—— any（）配合生成器，秒殺 go 語言循環判斷短路。

核心處理邏輯

  這塊代碼又可以分成 3 個部分：

Telegram 消息處理

 第 1 部分自然是針對消息本身，因為語音也是文件的一種，所以跟之前有些類似的就是要獲取 file_id；同時在權限上判斷語音消息的發送人限制為有限的用戶，如果不是就直接無視該條語音。

識別語音

 第 2 部分就是真正的語音識別了，核心就是中間 mlx_whisper.transcribe 那段，有幾個地方可以說下：

  1. 在測試識別語音工能的時候，不管我說什麼，識別的結果都是“**請不吝點贊 訂閱 轉發 打賞支持明鏡與點點欄目”，我以為是這個模型識別不太行，其實只是模型出現了”幻聽現象“——被 Whisper 模型誤認為了「背景雜音」或「靜音段落」，出現的內容是訓練時用到的大量的 Youtube 視頻。在處理微弱聲音時為了加快響應速度，而自行“腦補**”。瞭解到原因後，我就馬上意識到，肯能是我說得太小聲。重新發送語音後，確實能夠識別到準備的信息。並且在程序里加入 initial_prompt 這個參數 ，給大模型一個暗示，指明識別的方向；

  2. 比較坑的參數是 beam_size=1。這個值最開始為 5，改為 1 是 AI 建議說可以優化識別的速度，但是改了之後就報錯 Beam search decoder is not yet implemented。錯誤的解釋是 MLX-Whisper 的版本相容性問題，直接註釋掉，配合 initial_prompt 後續沒怎麼出問題；

  3. 誠如註釋裡所言，使用 to_thread 避免 MLX 計算時阻塞 Bot 的回應，最初的代碼是直接調用 mlx_whisper.transcribe 方法，方法里加入現在的參數，不用也影響不大。不過既然 AI 提醒了，那就順他的意思加一下，畢竟放到現實裡這也算是白嫖的服務。

關鍵字匹配結果

 這段就沒啥好說了，就是調用上文的匹配方法，給出一個結果和信息，方便後續操作。

縫合

  好奇的人可能已經發現：開頭的程序使用 go 冩的，怎麼後來又用 python 了？

  正所謂“**人生苦短，我用Python**”，Python 的簡單上手是出名的，在冩這種完全沒基礎的代碼時候肯定想著先快速冩出來看看是啥樣的，對此，Python自然是第一順位。而且，別忘了，這裡還涉及到大模型這種 AI 人工智能的需求，用 Python 豈不是水到渠成？

  那麼用 go 能不能冩這種方面的代碼？答案肯定可以，但是沒必要。雖然整體項目的大框架是 go，語音識別的部分已經拿原本就貼合的 python 冩完了，那麼現在重要的是如何縫合？測試的時候，python 裡是所有流程的完整代碼，實際上，真正需要 python 做的，也就是調用大模型進行語音識別的核心一小部分。除此之外的邏輯，比如人員限制、關鍵字匹配、結果處理都可以交給 go。算力和邏輯的解耦，就是最終實現的目標。

  不過可惜的是，雖然本人很想做這一塊，但根據領導要求暫時還沒有必要做到這個程度，我也僅僅本地跑通一個 go 調用 python 接口的 demo， 這一部分只能容後再議，期待下一次能真的實踐一下！
