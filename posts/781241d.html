TG 機器人重構

更新於2026-05-22|devops
|字數統計:3.1k|閱讀時間:13分鐘|瀏覽量:

  自從把機器人上雲以來發現並無什麼嚴重問題，偶爾有沒有觸發或者觸發失敗的 bug，也是因為冩代碼時候考慮不周——畢竟這玩意兒沒人測試，輸入的文本情況也比較複雜，當時很難考慮到所有情況。領導前一段時間也可能比較忙，沒空管這個，現在覺得需要優化一下，問問我有啥想法。

  結合我之前看到的代碼，我覺得主要有 2 點急需調整，也就是我接手代碼時就發現的問題：

  1. 機器人需要操作不同服務器的不同項目目錄，之前的代碼都是把映射關係通過 Struct + Map 的方式硬編碼在代碼中，這樣每次添加新的項目都需要修改代碼，非常不方便。
  2. 機器人對操作消息的分類方式不夠靈活，比如要操作Jenkins、系統服務、執行SQL等，而且不同操作的參數也不太一樣。分類通過 switch + case 就可以，再配合參數的個數，執行具體的操作。

  當時得到的回覆是他冩這塊代碼的時候屬於趕鴨子上架，而且站點項目不多，就圖一個方便沒考慮這麼多。那我也不好說什麼，畢竟剛進公司，人微言輕，萬一領導冩代碼時候有其他的考量呢？現在既然讓我放開手腳，那我肯定要想這麼提高拓展性，才能做到 **能不動代碼就不動代碼，要動代碼也要少動代碼**。

  我把我的想法和大概的實現方式和領導說了一下，領導覺得可以，於是我就開始著手重構，並且記錄一下整個修改的過程，方便後續回顧和優化。

  相較而言，第一個問題肯定是二者之中更為簡單的，所以先從這裡下手，本文也先只介紹這一部分。整個過程大致分為以下 3 個步驟：

定義配置文件

sites.yaml

 這裡貼出最基本的內容，可以看出如果有其他站點，或者某一個站點需要改動，直接依葫蘆畫瓢複製修改即可。當然，怎麼設計內容和結構，自然是經過一些思考和權衡的：既要清晰易懂，又要考慮代碼裡的解析和使用。除此之外，像 .mysql_info: &mysqlConn 和 .redis_info: &redisConn 是 YAML 的錨點，實屬學到的新技巧。用於減少重複代碼，只要再文本中引用 &mysqlConn 和 &redisConn 即可，畢竟基本的信息（如地址、端口、用戶名、密碼等）一般都不會變動，每個站點單獨配置自己的數據庫即可。

services.yaml

 sites.yaml 中每個站點包含的信息其實很多，需要花點心思設計；而 services.yaml 就沒個必要，反正就是固定的內容，純屬文本記錄，方便增減。

創建結構體

sites.go

 代碼本身沒啥好說的，純純通過 Viper 的標籤做字符映射；GetUniqueTaskTypes() 和 GetAllSiteAlias() 兩個方法也僅僅是為了方便後續使用。值得多說一句的是工具的使用：這種標籤映射冩法很死板，但如果定義的結構體字段比較多，哪怕使用快捷鍵 CV 大法，修改也挺麻煩的。好在我用的是 Windsurf——Vscode 的魔改版本，官方宣稱最大的特色可以利用 AI 分析整個項目，然後自動生成代碼。別的地方好不好用我不知道，不過用在這裡確實挺香的，直接讓我少冩了很多重複的代碼，只需要檢查一下標籤和數據結構是否正確，大大提高了開發效率。

service.go

 此處同理，不過 services 簡單，仿照 sites 裡冩 2 個方法用於後續邏輯代碼使用。

config.go

 最後在 config.go 裡把剛才定義的加上，注意這裡定義的是 Map 類型，Sites 的 key 是 a8/a1 這種，SystemServices 的 key 是 a/t 這種。其實 SystemServices 不用 Map 也行，不過 Sites 最好用，畢竟站點後續可能會加很多，用 Map 查找的話會比遍歷數組更快。這也就是我在 sites.yaml 裡定義站點時，並沒有用 - 增加多個站點信息的原因。

解析並熱加載

viper.go

 原來的程序我儘量不改動，只是定義了數組，將單一配置文件讀取改為多個配置文件讀取（我也有想過不是手動定義數組，而是通過查找指定目錄下所有 yaml 文件，後來覺得也沒啥必要，畢竟配置文件就那幾個，手動定義更直觀且不容易出錯），並且把讀取解析和監控熱加載都抽取成函數，這樣邏輯上比較清晰。

 讀取多個配置文件和單個配置文件邏輯基本一致，不過需要 MergeInConfig() 來實現合併。最後的全局鎖，用於安全更新配置，避免併發訪問導致數據不一致。當然，加了之後項目中其他地方讀取 global.GVA_CONFIG 時也需要加鎖。

 這裡就是監聽配置文件變動的邏輯，當配置文件變動時，會觸發 ReloadAllConfig() 函數重新加載配置文件。其中防抖機制是為了避免頻繁觸發 reload（比如 vim 修改文件），導致性能問題。同時，針對重命名的 Inode也做了處理，避免監聽失效。

  綜上，這一部分的優化到此就算結束了。當然，實際冩代碼的時候並沒有這麼順利，比如剛開始只監聽了一個配置文件，又或者監聽成功了，實際運行的數據並沒有更新……值得一提的是，這次大部分的代碼都是在谷歌瀏覽器的 AI 搜索聊天完成，我闡述需求、想法和問題，它不斷地改進、調整和優化。不敢說現在的代碼就是完美的，但至少程序運行一段時間之後，沒有出現任何問題。而且經過這次重構之後，無論是維護還是修改數據，確實方便很多。由此可見，AI 輔助編程確實能大大提高開發的效率和準確率。
